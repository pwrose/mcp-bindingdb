How to run¶

Keep the notebook in its folder, which holds everything it needs: requirements.txt (mcp-bindingdb at its commit and the versions of the packages it needs), the recorded results in data/ and the figures in figures/. With uv, from that folder (replace the path with yours):

cd /path/to/4.6-ligand-clustering-notebook
uv run --no-project --with-requirements requirements.txt --with jupyterlab jupyter lab 4.6-ligand-clustering-notebook.ipynb

then choose Run → Run All Cells. The first start installs the packages, which takes a minute or two; the cells show the recorded results, so no database is needed. Without uv: pip install -r requirements.txt jupyterlab, then jupyter lab 4.6-ligand-clustering-notebook.ipynb in the folder.

How to rerun the calls¶

To rerun every BindingDB call on your own copy of release 202610 and check each result against the recorded one, set RERUN = True in the setup cell and run all cells, or rerun the notebook without opening Jupyter, writing a copy with the new results:

cd /path/to/4.6-ligand-clustering-notebook
BINDINGDB_RERUN=1 uv run --no-project --with-requirements requirements.txt --with nbconvert jupyter nbconvert --to notebook --execute --output 4.6-ligand-clustering-notebook-rerun.ipynb 4.6-ligand-clustering-notebook.ipynb

A rerun needs the database: the one BINDINGDB_DUCKDB=/path/to/bindingdb_202610.duckdb names (put it before uv run), else the newest one mcp-bindingdb built on this computer, for example for Claude Desktop. With neither, the first rerun builds one, which takes about half an hour and 2.4 GB. To build exactly release 202610, with a clone of mcp-bindingdb:

git clone https://github.com/pwrose/mcp-bindingdb.git
cd mcp-bindingdb
git checkout 8b42a41f349a21988dcd2e1cfc7847ee93158b35
scripts/build_duckdb.sh --release 202610

The setup cell checks the database's release and source checksum against the recorded ones.

Run as it is, each call cell shows its recorded result, read from data/ and checked against the SHA-256 digest recorded in the cell. Rerun, it shows the new result with ✅ when it matches the recorded one (floats to 10 significant digits, ids of viewers and files left out). Calls to PubChem, RCSB or PDBe depend on those services and may differ. The prose answers are the model's and are not recomputed.

🧠 Assistant

Yes — scaffold keying splits these series apart.

Over the same 2,814 compounds there are 1,258 distinct Bemis-Murcko scaffolds against 826 clusters, so grouping by scaffold produces 1.5 times as many groups as clustering does.

The reason is visible inside a single cluster: cluster 4's 48 compounds carry 8 different Bemis-Murcko scaffolds between them, because the scaffold includes the ring substitution pattern — a 7-methoxy and a 7,8-dimethoxy quinoxaline are two scaffolds but one series to a chemist. Clustering on the fingerprint keeps them together; scaffold keying files them separately and would make the series look 8 times less explored than it is.

The two views answer different questions. Use group_by_scaffold to ask which exact ring system a compound is built on; use cluster_ligands to ask how many distinct series exist and to pick one representative from each, as in the figure — which draws the six centroids with the structures and potencies the clustering itself returned.

Read those bars as typical, not best: a centroid is the compound with the most neighbours in its cluster, so cluster 3's centroid sits at 100.0 nM while the series reaches 0.1 nM. Each panel names its cluster's best compound underneath.
